# How the daily automation works

Neither the daily log nor the forecast log is generated by a GitHub
Actions job calling an LLM API. Both are produced by a **Claude Code
agent** — the same kind of coding agent used to develop this repo —
running on a schedule via a Claude Code Routine (a scheduled trigger),
doing real research and a real commit each day.

need reconciling, and the honest fix at that point is to pick one source of
truth rather than to let both drift.

Each firing spawns a **fresh** Claude Code session (`create_new_session_on_fire`)
with no memory of prior runs — the standing instruction below and this
file are its only context — and access to the repo plus real web
search/fetch. In one pass, it:

1. **Researches and writes one daily entry** — a specific, non-generic
   finding from arXiv, an engineering blog, or a trending GitHub repo —
   following `data/daily/TEMPLATE.json`, and adds a row to
   `data/daily/index.json`.
2. **Resolves any due forecasts**: for every `data/forecasts/*.json` with
   `status: "open"` and `resolution_date` today or earlier, checks the
   `resolution_criteria` against reality and edits the file in place
   (`status: "resolved"`, `outcome`, `resolution_note`) — never deletes
   or replaces it.
3. **Writes one new forecast**, but only if it's been 7+ days since the
   last one or fewer than 3 are currently open — keeps the forecast log
   from either going stale or turning into noise.
4. **Regenerates everything derived from the JSON**: `python3
   scripts/build_feed.py` (refreshes `feed.xml`) and `python3
   scripts/build_pages.py` (refreshes `entries/*.html`, `forecasts/*.html`,
   `tags/*.html`, `sitemap.xml`). CI fails the build if either drifts from
   the JSON source of truth.
5. **Commits and pushes directly to `master`** in one push. It's fine for
   step 1 to be skipped on a day with nothing genuinely worth writing;
   step 2 and the regeneration step are never skipped if anything changed.

GitHub Pages serves the update automatically — either via the legacy
branch-deploy path, or via `.github/workflows/deploy-pages.yml` once
Settings → Pages → Source is switched to "GitHub Actions".

## Why direct-to-master

The content is low-stakes (a research digest, not user data or
infrastructure), every change is a single additive JSON file plus one
index row, and git makes any bad entry trivial to revert. That tradeoff —
skip a review queue in exchange for the pipeline actually being autonomous
— was a deliberate choice, not an oversight. If that stops being the right
call (e.g. entries need editorial review before publishing), switch the
final step to opening a PR instead of pushing straight to `master`.

## Why forecasts stay agent-native

`data/forecasts/*.json` is a second content stream, same shape as the
daily log, but for tracked predictions instead of synthesized learnings.
It deliberately stays agent-native rather than adopting a dedicated
forecasting library (e.g. Metaculus's `forecasting-tools`) — no new
runtime dependency, same mechanism (and now the same daily Routine) as
everything else on this site. `resolution_criteria` on every forecast
must name an exact, checkable public fact — if that can't be written
precisely, the question isn't specific enough yet.

## Adjusting the schedule

The Routine's cron expression, prompt, and enabled state can be changed
with the `claude-code-remote` MCP server's `update_trigger` tool (or
disabled entirely with `enabled: false`) without touching this repo. The
current prompt is reproduced here so it stays reviewable in-repo even
though the source of truth is the Routine itself:

> You maintain the live static site at github repo
> thepandorabox/thepandorabox.github.io (GitHub Pages, served from
> `master`). This is your daily maintenance run — a fresh session with no
> memory of prior runs. Start by reading AUTOMATION.md at the repo root;
> it documents the full content model, schemas, and conventions
> referenced below. Clone/pull the repo at `master` if you don't already
> have it checked out.
>
> Do all of the following in one pass:
>
> 1. **Daily entry.** Research one specific, non-generic recent
>    development in agentic AI architecture — an arXiv paper, an
>    engineering blog post, or a trending GitHub repo — using real web
>    search/fetch. Write `data/daily/<today's-date>.json` following
>    `data/daily/TEMPLATE.json` exactly. Only cite sources you actually
>    fetched and read. Add a matching row to `data/daily/index.json`.
> 2. **Forecast resolution.** Check every `data/forecasts/*.json` with
>    `"status": "open"`. For any whose `resolution_date` is today or
>    earlier, research the `resolution_criteria` against what actually
>    happened and edit the file in place: `status: "resolved"`,
>    `outcome: true/false`, `resolution_note` with a citation. Never
>    delete or replace the file.
> 3. **New forecast** — only if it's been 7+ days since the newest
>    `created` date across `data/forecasts/*.json`, or fewer than 3 are
>    open. Follow `data/forecasts/TEMPLATE.json` exactly. Add a row to
>    `data/forecasts/index.json`.
> 4. **Regenerate derived files**: `python3 scripts/build_feed.py` and
>    `python3 scripts/build_pages.py`.
> 5. **Commit and push directly to `master`.**
>
> If step 1 genuinely has nothing worth writing, skip it rather than
> force low-quality content — but never skip step 2, and always run the
> generator scripts and push if any JSON file changed. Don't fabricate
> sources, dates, or outcomes anywhere in this run.
